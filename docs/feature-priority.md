# 収益直結機能の優先順位

作成日: 2026-05-31

---

## 考え方：機能は3つの役割に分類できる

```
集客機能     → 無料ユーザーを増やす（間接的に収益へ）
転換機能     → 無料→Proへ押し上げる（直接収益に直結）
法人化機能   → Pro→法人へ押し上げる（最大単価）
```

---

## P0：転換の核（これがないと誰も払わない）

**Excel出力 ＋ 削除時自動行詰め・コメント連動削除**

この2つは事実上セット。Excel出力単体では既存ソフトと差がない。
「削除したら自動で整形される」という体験が初めて「これは違う」と感じさせる瞬間になる。

収益への影響：**Proプランへの転換率を決定づける唯一の機能。**
ここを後回しにすると、他の有料機能がどれだけ揃っても転換が起きない。

---

## P1：転換の後押し（あると転換速度が上がる）

| 機能 | 役割 | 理由 |
|---|---|---|
| 写真自動圧縮 | 即効性のある体験価値 | アップロードするたびに恩恵を感じる。毎日使う機能 |
| PDF出力 | 提出書類の完結 | Excel不要な現場でもPDFは使う。転換のもうひとつの動機になる |

この2つは「Proにしたら台帳作成が全部終わる」という感覚を完成させる。

---

## P2：法人化のトリガー（Proから法人へ引き上げる）

| 機能 | 役割 | 理由 |
|---|---|---|
| Google Drive連携 | チーム共有の入口 | 個人がDropbox代わりに使い始め、「会社のDriveにも保存したい」という需要が法人契約の前兆になる |
| 複数ユーザー共有 | 法人プランの本体 | これを必要とした瞬間が法人プランへの転換点 |
| 権限管理 | 法人契約の必要条件 | 会社として契約する際に管理者が求める機能 |

---

## P3：集客の核（無料ユーザーを獲得・維持する）

| 機能 | 役割 | 理由 |
|---|---|---|
| ガイドオーバーレイ撮影 | 口コミの発生源 | 「同じ画角で撮れる」体験は現場で見せると驚かれる。現場の口コミは最強の集客 |
| 施工前後比較 | 継続使用の動機 | 写真が蓄積されるほど価値が増す。データが溜まるとやめにくくなる |

これらはすでにMVPに含まれており、**集客コストゼロで口コミを生む設計**になっている。

---

## P4：あると良いが後回しでよい

| 機能 | 理由 |
|---|---|
| 工事看板挿入 | 差別化にはなるが、台帳作成の本質ではない |
| 管理者ダッシュボード | 法人契約後の満足度向上。契約獲得には直接不要 |
| 独自テンプレート共有 | 法人の継続率を上げる機能。獲得フェーズでは不要 |

---

## 開発順序の推奨

```
Phase 1（MVP）
  ガイドオーバーレイ ＋ 施工前後比較 ＋ タグ管理
  → 無料ユーザーを獲得し、口コミを発生させる

Phase 2（最優先）
  Excel出力 ＋ 削除時自動行詰め・コメント連動削除
  → 初めてお金が入る。ここが事業の起点

Phase 3
  写真自動圧縮 ＋ PDF出力
  → 転換速度を上げる。Proの「全部入り」感を完成させる

Phase 4
  Google Drive連携 ＋ 複数ユーザー共有 ＋ 権限管理
  → 法人収益の柱を作る

Phase 5
  工事看板挿入 ＋ 管理者ダッシュボード ＋ テンプレート共有
  → 満足度・継続率の向上
```

**Phase 2のExcel出力が最速で収益化できるか否かを決める。**
ここの完成度（特に削除時の自動整形）が競合との差になるため、工数を惜しまない判断が必要。

## 将来改善項目：写真原本の外部バックアップ対応（2026-10-12 記録・仕様未確定・未実装）

**現時点では未実装・仕様未確定です。調査結果はすべて検討メモであり、実機では未検証です。**

- **目的**：端末交換・故障・ブラウザデータ削除による写真原本の消失リスクを減らす。現状、写真原本は端末の IndexedDB のみで、クラウドには 600px 圧縮画像しか保存されない（`docs/current-spec.md` 4.2節）。
- **第一候補**：端末の写真フォルダへの原本保存と、Googleフォトのバックアップ機能の活用。
- **第二候補**：Google Drive API 連携。
- **実装時期**：Helper 1.1.0 および Web 新レイアウトの正式リリース後に検討。

### 区別すべき3つの状態
| 状態 | 意味 |
|---|---|
| ① 端末の写真フォルダへの保存 | 端末内にファイルができただけ |
| ② Googleフォトへのバックアップ完了 | Googleフォト側の設定・フォルダ・通信状況で決まる別の状態 |
| ③ Google Drive へのアップロード完了 | API の応答で判定できる状態 |

①は②や③の完了を意味しない。フォルダに保存できたことだけで、Googleアカウントへの同期完了とは判定しない。

### 方式の比較
| 観点 | A：端末の写真フォルダ＋Googleフォト | B：Google Drive API |
|---|---|---|
| React PWA での実現性 | 制約が大きい。PWA から端末の任意フォルダ（ギャラリー）へ自動保存する標準手段はない | 実現可能（OAuth ＋ REST。Google Identity Services） |
| Android Chrome | ファイル保存は「ダウンロード」経由が基本（保存先は Downloads）。フォルダ選択 API は Android Chrome では使えない前提で要確認。ダウンロード先がGoogleフォトのバックアップ対象かは設定次第 | 動作する。認証画面と権限許可が必要 |
| iPhone Safari | 自動保存不可。共有シートの「画像を保存」で写真ライブラリに入れる手動操作が必要（保存後はGoogleフォトの設定次第でバックアップされ得る） | 動作する（認証はポップアップ/リダイレクトの制約に注意） |
| ユーザー操作 | 毎回または一括の保存操作が必要になる公算が大きい | 初回のGoogleログイン・許可のみ。以降は自動アップロード可能（トークン更新の扱いに設計が必要） |
| 保存先フォルダ | 端末依存。アプリが指定できない | Drive 内にアプリ専用フォルダを作れる（`drive.file` スコープ想定） |
| Googleフォトのバックアップ条件 | ユーザーがGoogleフォトのバックアップを有効にし、対象フォルダが含まれることが前提。**Webからは完了を検知できない（②は判定不能）** | 不要（Drive に直接保存） |
| Google認証 | 不要 | 必要（OAuth 同意画面の設定・審査の要否を要確認） |
| 完了の判定 | ①のみ判定可能 | ③を API 応答で判定可能 |
| 実装難易度 | PWAのみでは低〜中だが体験が不完全。確実にするなら Capacitor 等のネイティブラップが必要で高 | 中（認証・アップロードキュー・再試行・クォータ） |
| 維持費 | なし（ユーザーの端末・Googleフォトの容量） | API 自体は無料枠内の見込み。ユーザーの Drive 容量を消費。審査・保守の工数 |
| IndexedDB との関係 | 原本は引き続き IndexedDB に保持 | 同左。IndexedDB から読み出してアップロード |
| 二重保存 | 発生（IndexedDB ＋ 端末フォルダ） | 発生（IndexedDB ＋ Drive） |
| 写真削除時 | アプリ側で端末フォルダの写真は消せない。残るのが通常 | アプリが削除するか、Drive 側に残すかを方針として決める必要あり |
| オフライン時 | 保存は可能（①）。バックアップ完了（②）は復帰後 | アップロードを待機キューに入れ、復帰後に再開 |

### 推奨（暫定）
- **完了を確実に検知でき、PWA 単体で実現できるのは B（Google Drive API、`drive.file` スコープ）。** A は PWA では手動操作が前提で、②を判定できないため「バックアップ済み」とは表示できない。
- 第一候補を A とする場合も、「共有シート/ダウンロードで端末に保存する補助機能」として位置づけ、バックアップ完了とは表示しない。自動化したい場合はネイティブラップを検討する。
- 実装前に、Android/iPhone の実機で A の保存先とGoogleフォトの対象フォルダを検証し、OAuth の審査要否・トークン更新方式・Drive 容量の案内を確認する。上記の仕様は変更され得るため、着手時に最新の公式情報で再確認すること。
